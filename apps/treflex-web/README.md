# Treflex client

A t3code web client built on treflex (the framework in [the reflex repo](file:///G:/Sorted/Code/reflex)) and Solid, against the stock t3code server. It's Tam's daily driver, and a test of treflex on an app it wasn't designed around.

Log gaps and problems in [docs/issues.md](./docs/issues.md).

## Decisions

| Decision           | Choice                                                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Repo               | Private `Tgoh/t3code`, not a public fork, because treflex is unpublished                                                                                                                         |
| Branches           | `main` only tracks upstream. `treflex-main` is the working copy the daily driver runs from; changes go on worktree branches and merge back once they pass the gates, and a bad merge is reverted |
| Location           | `apps/treflex-web`. Avoid editing upstream's files so merges stay easy                                                                                                                           |
| Renderer           | Solid, through `treflex-solid`                                                                                                                                                                   |
| Reused             | `packages/contracts`, `packages/shared`, and `client-runtime`'s `connection/` and `rpc/`                                                                                                         |
| Replaced           | `client-runtime/src/state`, the Zustand stores, and the web components                                                                                                                           |
| Server             | No server changes. If something seems to need one, log it in `issues.md` first                                                                                                                   |
| State              | Hold the wire format in the tree, with no decoded `DateTime`, to meet treflex's plain-data rule                                                                                                  |
| Reducer            | Written as treflex actions that mutate the tree, not a port of the immutable reducer                                                                                                             |
| Tests              | Headless, with a scripted server at the effect boundary                                                                                                                                          |
| Terminal emulator  | `@xterm/xterm` and its fit addon, loaded on first open. Stock's libghostty WASM surface isn't reusable from a non-React app without its build and surface code                                   |
| Project order      | `localStorage`, like stock's `projectOrder` in `uiStateStore` and its `sidebarProjectSortOrder` client setting. Neither is on the server, so neither is shared with stock or other devices       |
| Treflex dependency | `treflex` and `treflex-solid` 0.2.0 from npm, pinned to the exact version. `treflex-eslint` is a tarball in `vendor/`, installed with `file:`, since builds between releases aren't published    |

The server holds all the work, and the client receives its data and uses treflex for client state.

## Architecture

Read [overview.md](../../docs/internals/overview.md), [connection-runtime.md](../../docs/internals/connection-runtime.md) and [performance-regressions.md](../../docs/internals/performance-regressions.md) first.

- **Server:** `Orchestrator.ts` decides events, `EventSink` commits events, projections and the outbox in one SQLite transaction, and `EffectWorker` runs side effects afterwards. It has to work with no client connected.
- **Transport:** `WireProjection`, `ShellStream`, `ThreadStream` and `ThreadLiveEventCoalescer` shape what each subscriber receives. This is the client's input contract.
- **Stock client:** `client-runtime/src/state/threads.ts` and `shell.ts` hold snapshots, cursors and caches. `orchestrationV2Projection.ts` is the immutable reducer this client replaces.

An approval is a server row (`OrchestrationV2RuntimeRequest`) that the client displays and answers with a command. Don't model it as a parked `ask`: that wouldn't survive a reload, and another device can answer it.

## State model

If the server can rebuild it, it's replica. If only this client knows it, it's local.

```text
Root
└─ Environment
   ├─ Replica            (server's data, read-only here)
   │  ├─ Shell: projects, thread rows
   │  └─ OpenThreads: runs, messages, turn items, requests (selected and recently left)
   └─ Local              (only this client knows it)
      ├─ ThreadSessions: draft, attachments, panels; diff panel, terminal, git work, git status
      ├─ Dictation: the microphone and the server's voice models
      └─ Preferences, sidebar shelves, system scheme
```

The minute clock isn't in the tree: it's the `Minute` outside value (`Infrastructure/clock.ts`), which views and selectors read with `minute`, since no work starts from it. An action that needs the time reads the `clockNow` effect.

- **Only what arrives from the server writes to the replica:** the stream receivers (the server config among them, which also derives the composer's provider list and favorites), history pages, an open thread's lookup of its lineage titles, settings writes' replies, plus opening and closing a thread. The Archive and Usage pages hold what they read in their own component state (`ArchivedThreads.ts`, `UsagePage.ts`), which goes when the page closes. Commands change it only through what the stream delivers next. A thread's own commands are `ThreadSession` actions, so their draft can't reach the replica. An answer runs on its runtime request's entity, but writes only a transient error, which sits in the `TransientState` root rather than the replica. `REPLICA_WRITERS` in `testing/threadFixture.ts` lists the writers, and any `Model.test.ts` test fails when another action writes the replica.
- **Data about running work isn't state.** Busy marks are `inFlight` reads, which views make with `useInFlight` and only a selector combining busy with other state, such as `diffLoading`, makes itself. Stream sync is a transient, and a stream's end is read from its resource status.
- **A failure with its own place on screen is caught where it happens,** as a send's or an answer's is. Such a `catch` takes only a `ServerError`, through `serverError(error)` in `Infrastructure/serverError.ts`, which rethrows a refusal or a bug. The effect implementations make every server or network failure one: `settle` for an Effect run (a typed failure is the server's, and so is an interrupt, since one the action asked for never reaches it; a defect is a bug), `serverFetch` for `fetch`. A `ServerError` is a plain `Error` named `ServerError`, made with `serverFailure`, never a subclass: treflex hands an action a copy of what an effect rejects with, which keeps the name but not an app class, and a development build or a test reports `effect/class-rejection` for a class. Anything else below `Root` throws to `Root`'s `Action/Error` boundary, which shows the latest one in the sidebar until it's dismissed. `Root`'s own `load` failing reaches the empty `onError`. Every caught throw, taken or not, is logged from the runtime's `failure` event in `index.tsx`.
- **Entities stop at the open thread, except its runtime requests, its secret and link cards (`ItemRequests`, by turn item id, since the server keeps no request row for them) and its history window,** whose busy marks have to be their own (see `issues.md`). `reconcileEntities` and `putEntity` in `rows.ts` mint new requests and fold held ones in place.
- **A typed secret or pairing code never enters state.** The secret stays in its input and the code in the dialog's component state until the answer action takes it as an argument. The answer effects are `redact: true`, and their failures keep only the server's own message, never the cause, which can echo the request. Runs, messages, turn items and shell rows are plain wire data, held by `id` in records and folded in place with `reconcile` in `rows.ts`. The timeline holds item ids, and each row joins itself with `timelineItem` and decides its own visibility, so a delta costs the same at any thread length. Grouping is laid out per response (a prompt to the next), from per-row facts that stay equal through text deltas, so a delta re-lays only its own response. A parent selector over the rows also leaves deltas alone if it returns stable references, because `<For>` remounts on new objects, but it walks the list on every added row, which only shows on very long threads.
- **A left thread stays in `OpenThreads` for five minutes,** as stock keeps it. Leaving closes its stream and starts its `Thread/Expire` timer, and returning stops the timer and reopens the stream from `LastSequence`, so the server sends only what was missed, or a snapshot past its replay limit. The tick publishes `Thread/Expired`, and `Environment` removes the thread unless it's selected again. Being in `OpenThreads` doesn't mean being on screen, so `restoreTerminal` reads the selection through the `Selection` data source.
- **Drafts are Local and kept in `localStorage`,** per thread id, as stock keeps them: `ThreadSession` writes the text and picks on each change and the attachments after each add or remove, and `Environment.sessionOf` fills a new session from them. A new-thread draft keeps its project, so returning to that project's new thread restores it under the same id.
- **This device's choices are Local too,** in `Local.Preferences`: the sidebar's grouping, sort, manual order, hidden projects, project filter, closed folders, collapse and width, whether the details card is pinned, the appearance mode, the usage page's metric and window, and the providers whose compaction offer was answered "Don't ask again". `newEnvironment` reads them through `storedPreferences`, and each change writes its fields through `storePreferences`, under the `localStorage` keys and shapes they always had, which stock shares for the theme, usage page and sidebar width. The thread order the sidebar shows and the next and previous shortcuts follow is the `sidebarLayout` selector.
- **Local state doesn't sit under replica threads.** Treflex treats removal as disposal, and a thread can be trimmed from the shell while it still exists. A draft also exists before its server thread does.
- **Deleting a thread is two linked steps.** The delete's reply forgets the `ThreadSession`, its stored draft and the selection. The streams remove the replica's rows: the shell's `thread.removed`, and an open thread's `thread.deleted`, whose receiver also forgets the session when another client deleted it.
- **A session joins the replica through the `Replica` data source,** which `Environment` registers, in selectors. An action reads those selectors with `select`, because a direct `getData` in an action copies the whole replica.
- **Dictation is one microphone for the client,** owned by the `Dictation` entity's `Voice/Dictation` resource, which runs stock's `VoiceInputController` from `client-runtime`. Its phase and the thread it records into are that entity's `Recording`, so a recording keeps going while another thread is selected, and its transcript goes to the environment, which puts it in its own thread's draft. The level and live text stay in the resource's exposed value, outside state. The entity also holds the server's voice model list, which Voice settings shows and a start checks for a model in use, so a download's progress outlives the page.
- **Terminal and command output never enter state.** The `terminalSession` resource owns the emulator and its socket traffic and emits only lifecycle status. `commandOutput` exposes its text, on an entity `toggleRowExpanded` mints for the row, and lives while the row is expanded and its thread shown. Hiding the panel or selecting another thread detaches, and `localStorage` remembers each open panel's launch so a return or a reload reattaches.
- **Applying one delta stays under a frame (16 ms) and doesn't grow with thread length.** `vp run bench` measures it.

### Mismatches with the server

1. **A missing row doesn't mean a thread is gone.** The shell leaves out idle subagents and older settled threads, so absence can't drive disposal or deletion.
2. **Whole-row replacement.** `*.updated` events replace whole rows, and reconnects can deliver snapshots. Assigning a payload over a held node replaces the node, so views over it remount, and treflex has no `merge`. These go through `reconcile` in `rows.ts`, which keeps the nodes of rows the payload still carries.
3. **One item in several places.** Items appear in `turnItems` and `visibleTurnItems[].item`, and inherited rows come from other threads. An entity has one parent, so use id references and selector joins.
4. **Events apply as in-place actions.** Assigning a new projection walks the whole thread on every event.
5. **An action holds its entity.** Other work on that entity queues behind it, so every network wait in an action on a session, environment, open thread or runtime request is wrapped in `open(...)`. Other work runs during the wait, so what follows re-checks its premises and re-finds nodes on the draft.
6. **Turn items are a discriminated union on `type`.**

## Running it

Run everything from the repo root with `./dev-stack.ps1`. It starts the server on 13773 without its file watcher, because a watcher restart interrupts running turns, plus this client on 5734 and the stock UI on 5733, as hidden processes that outlive the terminal. `-Status` shows what's up and `-Stop` stops what it started. State and logs are in `G:\Sorted\Code\t3code-dev-home`.

This client runs as a production build served by `vp preview`, not the dev server: a cold start on a phone takes about a dozen requests instead of hundreds. It has no HMR, so a change reaches it only through `./dev-stack.ps1 -Restart -Only treflex`, which runs `scripts/driver-build.ps1` to build into `t3code-dev-home\dev-stack\treflex-next` and swaps that into `apps/treflex-web/dist` only when the build succeeds. A failed build exits 1 and leaves the running client and `dist` alone; its output is in `dev-stack\treflex-build.log`.

Production builds register a service worker (`src/sw.ts`, which `vite.config.ts` writes to `dist/sw.js` with the build's file list). It precaches the shell, caches hashed assets as they load, and fetches `index.html` network-first, falling back to the cached copy offline or after three seconds. It handles only those files and page loads, never `/api`, `/ws`, `/oauth`, `/.well-known`, `/mcp` or another origin. A new build is used from the next launch or reload; the new worker installs in the background and drops the old cache. A page left open on an old build reloads itself if it needs a chunk the rebuild removed. The dev server never registers it.

The server looks for a built web client in `apps/web/dist` once, at startup, and `claude mcp login` needs it for the approval page. Build it with `vp build` in `apps/web`, with no `VITE_HTTP_URL` or `VITE_WS_URL` set, and restart the server if a sign-in says no static directory is configured.

Tailscale Serve exposes this client on the machine's tailnet address at port 8443 (port 5734) and that built stock client at `:8444` (the server on 13773). The stock one is Tam's fallback when this client is broken, since no change here can break it; don't remove it or rebuild `apps/web/dist` from a broken checkout.

The session cookie isn't tied to a port, so a browser paired on 5733 is already paired on 5734. Otherwise open `localhost:5734/#token=…` with a token from `node apps/server/src/bin.ts pair`.

From `apps/treflex-web`, `vp run test` runs the headless suite and `vp run bench` prints the benchmark against `applyOrchestrationV2ProjectionEvent`, on a generated long thread. A new resource that follows a server stream gets a row in `CASES` in `src/Infrastructure/sessionSwap.test.ts`, which checks that it moves onto the session a reconnect opens. Run them from there: from the repo root, vitest misses this app's Solid resolve conditions. `bench/stream` measures this client against stock in Chrome while a turn streams; its results are in [docs/benchmarks.md](./docs/benchmarks.md). [`bench/wire`](./bench/wire/README.md) checks the tree's codec against a running server's real data.

## Making changes

The client in the main checkout is the daily driver, so nobody edits files there. Each change gets a worktree off `treflex-main`, anywhere on disk. T3's worktree setup installs, or run `node scripts/setup-worktree.ts` with `T3CODE_PROJECT_ROOT` set to the main checkout. Then, from the worktree's `apps/treflex-web`, run its client against the same server:

```powershell
$env:TREFLEX_WEB_PORT = 5735; vp run dev
```

Keep test clients on 5735: `localStorage` is per port, so choices such as grouping by project stay set there across worktrees. The test client works on the driver's real threads, so a send there runs a real turn. The driver changes only when the branch merges into `treflex-main` and the driver is rebuilt.

To test what the driver will serve, including the service worker, build and preview on another port: `vp build`, then `vp preview --port 5747 --strictPort`. `localhost` counts as secure, so the worker registers without HTTPS. The worker outlives the server on its port, so unregister it in DevTools before running the dev server there again.

Work in the reflex repo doesn't reach this client until it's published. To move to a new release, read its breaking-changes record in the reflex repo's `docs/wip`, set both versions in `package.json`, and run `vp i`.

To bring in upstream changes, use the `/syncupstream` skill: it merges on a worktree, ports the logic copied from stock, tests the client live, and fast-forwards `treflex-main` only when it all holds. `apps/treflex-web/scripts/sync-upstream.ps1` alone fast-forwards `main` and pushes it to `origin` (`-DryRun` previews).

`upstream` is fetch-only. Actions is disabled on `Tgoh/t3code`, because upstream's workflows include release and deploy jobs. Keep it disabled.

## Styling

Tailwind v4 with preflight, like stock. `src/index.css` is the entry: it carries stock's whole `@theme inline` block, its custom utilities (`dropdown-glass`, `surface-glass`, `pt-safe` and the rest) and the `dark`/`light`/`any-hover` variants, over the tokens in `src/styles.css`, so a class copied from `apps/web` means the same thing here. `dark:` follows the `data-theme` attribute the appearance setting sets. `styles.css` has stock's tokens apart from those for features treflex doesn't have yet, such as the Electron window chrome, `@pierre/diffs` and `@pierre/trees`, Pele diagrams, the settings slider, the prompt font settings, the diff colour schemes, the ultrathink highlight, thread find and the theme presets. Stock's `[data-app-sidebar]` overrides are folded into the global `--sidebar-*` tokens. A stock token that isn't here renders nothing until it's copied the same way.

`styles.css` holds only global rules: the tokens, the page's base styles, the `.chat-markdown` prose rules for markup generated from Markdown (which can't carry utilities), the terminal's xterm overrides, and the iOS input rule. It sits in the `components` layer, above preflight and under the utilities, so its rules beat the reset and a utility always beats it. Preflight strips the heading, list and margin defaults, so the prose rules set them for Markdown.

- Put utilities in the markup. Never add a rule to `styles.css` unless it's global.
- When porting from stock, copy its class strings.
- Arbitrary values (`text-[14px]`) are fine where stock's scale would shift a pixel: stock's `text-sm` and `text-xs` also set a line-height.
- There's no `tailwind-merge`. Never put two utilities for the same property on one element: Tailwind's order wins, not the class order. Drive state through variants on the element's ARIA or data attributes (`aria-[current=page]:bg-accent`, `aria-selected:`, `data-[state=open]:`), not a `classList` that adds a competing utility.
- A class string used more than once in a file is a `const` at the top of that file. A look shared across areas becomes one exported string or component under `src/ui/`, made by the thread that owns it.
- `hover:` applies only where the pointer can hover, as in stock.
- Tailwind reads class names from the source text, so a class glued to an interpolation (`` `py-4${extra}` ``) is never generated. Leave a space before the `${`.
- To style an element by an ancestor's state, put the variant on the element (`in-[.chat-stage.with-details]:max-w-…`), not a rule that reaches into it.

### Shared controls

`src/ui/` holds the controls every area uses, each owning its look the way stock's `components/ui` do: `Button`, `InlineButton`, `Toggle`, `ToggleGroup`, `SidebarMenuButton`, `SidebarInput`, `Input`, `DraftInput` (commits on blur or Enter), `Textarea` (grows with its text), `InputGroup` with `InputGroupAddon` and `InputGroupInput`, `Label`, `Kbd` and `KbdGroup`, `Badge`, `Spinner`, `RefreshIcon` (spins while `refreshing`), `Skeleton`, `Select`, `WrapSelect` (for labels too long for a phone row), `Switch`, `MenuSwitch`, `Segmented` and `Segment`, the `Menu` parts (`MenuPopup`, items, checkbox and radio items, groups, `MenuSub` submenus, `MenuSearchInput`), `PopoverPopup`, the `Dialog`, `AlertDialog` and `Wizard` parts, and the tooltip host, which shows any element's `data-tip` (its `data-tip-*` attributes are listed on `TooltipHost`). Pick a `variant` or `size`, and pass `class` only for layout (margin, width, position) or a property the variant doesn't set. If no variant fits, add one there rather than restyling at the call site. `buttonVariants()` and `sidebarMenuButtonVariants()` return the class string for an element that can't be a `<button>`, such as a link or a label. A field's `class` goes on its `data-slot="input-control"` wrapper, as stock's does; mark a bad value with `aria-invalid`. A `Toggle`'s `pressed` prop sets both `aria-pressed` and `data-pressed`. A `MenuPopup` or `PopoverPopup` is placed against its `anchor` (an element, or a point for a context menu) and writes `data-popup-open`, `data-pressed`, `aria-expanded` and `aria-controls` on its trigger while open, so the trigger only owns its open state; render it in a `Presence` and close it from `onClose`, which items, Escape, Tab and a press outside all call. A menu with a trigger is modal, as Base UI's: a backdrop with a hole for the trigger takes outside presses, so nothing under it gets them. A context menu (a point and no trigger) isn't, as stock's: a right-click elsewhere closes it and opens that target's own menu. A menu trigger carries `aria-haspopup="menu"` and `aria-expanded="false"`, and passes its `onKeyDown` to `openMenuFromKeys` so ArrowDown and ArrowUp open it. Nested menus and popovers dismiss through the overlay stack in `overlays.ts`, top first. A `Dialog` or `AlertDialog` is a modal `<dialog>` in the top layer: render it in a `Presence` and close it from `onClose`, which Escape, `DialogClose` and, for a `Dialog` only, a press outside the popup call. It focuses the first `DialogAction` on open (else the first tabbable element), and gives focus back to its opener once it unmounts: the trigger, or for a menu item, the element that menu returns focus to. A surface inside a `Presence` passes `usePresence().track` as its ref and styles its entrance and exit with Base UI's `data-starting-style:` and `data-ending-style:`, as stock's class strings do. A `visible-animate-*` or `live-*` animation stays paused until its element is passed to `observeVisibleAnimation` from a ref, which runs it only while it's on screen in a visible tab.

## Setting up a machine

Two folders sit side by side under `G:\Sorted\Code`, because `dev-stack.ps1` finds the data folder by relative path, and the Claude skills use absolute ones:

- `t3code`: this repo, on `treflex-main`.
- `t3code-dev-home`: the driver's data (threads, settings, attachments, stored secrets, T3's worktrees). Copy it from the old machine with the stack stopped (`./dev-stack.ps1 -Stop`), or leave it out to start empty.

Install Git, PowerShell 7, nvm-windows and Vite+ (`vp`), then the Node version in the root `package.json` `engines` field:

```powershell
nvm install 26.13.1
```

```powershell
nvm use 26.13.1
```

```powershell
git clone -b treflex-main https://github.com/Tgoh/t3code.git t3code
```

```powershell
git -C t3code remote add upstream https://github.com/pingdotgg/t3code.git

git -C t3code remote set-url --push upstream no_push
```
